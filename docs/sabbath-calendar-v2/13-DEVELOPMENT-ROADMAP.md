# Development roadmap

All phases below describe future work except the source and document inspection in this package. Gates authorize an implementation sequence after owner review. Verification begins alongside each module.

| Phase | Scope and deliverable | Dependency and principal risk | Acceptance and definition of done | Owner action |
|---|---|---|---|---|
| 0 · Baseline | Freeze commit, inventory and fixture ledger. Identify independent almanacs and inspect provider/data license terms. | Existing source and drawing. Risk of adopting a neighboring project's changes or an incorrect anniversary. | Four-file baseline and fixture meanings recorded in [existing project analysis](02-EXISTING-PROJECT-ANALYSIS.md); tag all research gaps. | Confirm parity scope and approve commencement at item 1 in [owner approval checklist](16-OWNER-APPROVAL-CHECKLIST.md). |
| 1 · Core | Build integer types, floor arithmetic, exact inverse, cycle partition, strict/inclusive neighbors and transport validation. | Phase 0. Remainder behavior before A, unsafe parsing and negative zero. | G1 passes in two engines; publish reproducible property seeds and a standalone module with no date/DOM dependency. | Review G1 evidence before adapter integration. |
| 2 · Converters | Implement Gregorian and Julian first, then the Hebrew provider and Chinese table profile. Produce range manifests, reverse search, fixture lineage and exception handling. | G1, evidence rights, leap-month identity. | G2 passes per enabled adapter. Archive comparisons and qualified dates. A required row with no verified coverage prevents declaring full MVP ready. | Approve actual coverage, licensing and uncertainty text. |
| 3 · Timeline | Build one selection store, searchable rows, viewport, details and keyboard/mobile layouts. Publish a testable static preview. | G2 for verified labels. Precision loss in CSS or stale results. | T08–T11 pass, including the signed searches and stable element count. Review desktop and mobile walk-through. | Approve interaction semantics and accessible presentation. |
| 4 · Release verification | Run independent oracle, differential, compatibility, offline and usability suites against the actual static distribution. | Phases 1–3. Shared test lineage can mask identical bugs. | G1–G3 signed off, manifests and artifacts versioned, legacy assets intact, rollback consists of withdrawing V2 entry/assets. | Explicit release decision after reviewing evidence and outstanding risks. |
| 5 · Extensions | Optional local observance, named Creation models, additional adapters and sourced historical tracks. Each has its own schema and evidence. | Released core, model-specific sources and approvals. Polar exceptions and unsourced synchronisms. | G4 for each enabled extension plus regression of G1–G3. Annotation-only projects require separate provenance and uncertainty fixtures. | Opt in independently per extension. |

**MVP** comprises the unrestricted mathematical sequence, four calendar adapters within their declared coverage, legacy fixture compatibility, accessible direct navigation and static deployment. General historical reform selection, eclipse reconciliation, recorded-event ingestion, minute-by-minute observance and Creation boundaries belong to later work. No calendar row may silently substitute another calendar's date to meet a release deadline. [risk register](14-RISK-REGISTER.md)
